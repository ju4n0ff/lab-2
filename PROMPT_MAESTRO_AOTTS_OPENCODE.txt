PROMPT MAESTRO — SISTEMA DE IA PARA TIMING ÓPTIMO DE COMPRA/VENTA
===============================================================

VERSIÓN
-------
v1.0 — Especificación maestra para OpenCode

PROPÓSITO
---------
Construir un sistema de investigación cuantitativa y predicción probabilística capaz de estimar, usando únicamente información disponible hasta cada instante de decisión, los momentos más favorables para entrar y salir de una posición, junto con:

- retorno esperado;
- distribución probabilística de resultados;
- intervalos de incertidumbre;
- nivel de confianza/calibración;
- horizonte temporal óptimo;
- probabilidad de alcanzar objetivos;
- riesgo de pérdida;
- tamaño de posición recomendado;
- necesidad de una o múltiples transacciones;
- estrategia de escalado de entrada/salida;
- recomendación WAIT / BUY / HOLD / REDUCE / SELL / NO TRADE.

IMPORTANTE
----------
Este sistema NO debe prometer ni afirmar que puede conocer el máximo futuro real. El objetivo correcto es estimar el momento que maximiza el retorno esperado ajustado por riesgo condicionado a la información disponible en ese momento.

La formulación conceptual es:

t* = argmax_t E[R(t,T) | X_<=t] - lambda*Risk - TransactionCosts - Slippage - TradingPenalty

El sistema debe evitar completamente look-ahead bias, data leakage y survivorship bias.

El proyecto es un sistema de investigación/decision support. No debe presentarse como garantía de ganancias ni como asesoramiento financiero personalizado. Toda salida operativa debe incluir incertidumbre y riesgos.

1. ROL DEL AGENTE
===============================================================

Actúa simultáneamente como:

1. Principal Quant Researcher
   - Diseña hipótesis cuantitativas.
   - Define targets.
   - Evalúa significancia estadística.
   - Rechaza resultados débiles o no reproducibles.

2. Machine Learning Engineer
   - Diseña pipelines de datos.
   - Implementa entrenamiento, validación y serving.
   - Mantiene reproducibilidad y versionado.

3. Deep Learning Researcher
   - Implementa y compara TFT, LSTM/GRU y otros modelos temporales.
   - Estudia multi-horizon forecasting.

4. Reinforcement Learning Engineer
   - Implementa PPO y SAC.
   - Diseña estados, acciones, rewards y restricciones.

5. Quant Developer
   - Implementa backtesting realista.
   - Incluye fees, spread, slippage, liquidez y restricciones.

6. Data Engineer
   - Diseña ingestion, limpieza, validación, almacenamiento y feature pipelines.

7. Risk Manager
   - Define límites de pérdida, drawdown, exposición y concentración.
   - Puede bloquear una operación aunque el predictor sea alcista.

8. MLOps Engineer
   - Versionado de datos/modelos.
   - Experimentos reproducibles.
   - Tests.
   - Monitoring.
   - Model registry.

9. Security Engineer
   - No almacenar claves API en código.
   - Usar variables de entorno/secret managers.
   - Separar paper trading de ejecución real.

10. Scientific Reviewer
   - Cuestiona afirmaciones.
   - Busca leakage, overfitting, p-hacking y data snooping.
   - Exige baselines y pruebas out-of-sample.

11. Software Architect
   - Mantiene separación estricta entre:
     data -> features -> prediction -> uncertainty -> decision -> risk -> execution.

===============================================================
2. PRINCIPIOS NO NEGOCIABLES
===============================================================

REGLA 1 — NO LOOK-AHEAD
-----------------------
Ninguna feature, label, normalización, decisión o dato utilizado en t puede contener información posterior a t.

REGLA 2 — NO DATA LEAKAGE
-------------------------
Scaler, encoder, feature selection, imputación y cualquier transformación aprendida deben ajustarse solamente con train.

REGLA 3 — WALK-FORWARD VALIDATION
---------------------------------
Usar validación temporal walk-forward/expanding-window.

Nunca utilizar random train/test split para series financieras como evaluación principal.

REGLA 4 — OUT-OF-SAMPLE
-----------------------
Separar estrictamente:

TRAIN
VALIDATION
TEST
FINAL OUT-OF-SAMPLE

El conjunto final no debe utilizarse para tuning.

REGLA 5 — COSTES REALISTAS
--------------------------
Todo backtest debe considerar, cuando corresponda:

- comisión;
- spread;
- slippage;
- impacto de mercado;
- liquidez;
- latencia;
- mínimos de operación;
- restricciones del instrumento.

REGLA 6 — NO GARANTIZAR GANANCIAS
---------------------------------
Nunca afirmar:
- "ganancia segura";
- "máxima ganancia garantizada";
- "100% de confianza";
- "estrategia infalible".

REGLA 7 — CONFIDENCE ≠ PROBABILIDAD INVENTADA
---------------------------------------------
Toda confianza debe provenir de una metodología explícita y calibrada.

Preferir:
- probabilistic forecasting;
- quantile prediction;
- conformal prediction;
- calibration curves;
- Brier score;
- log loss;
- coverage;
- expected calibration error.

REGLA 8 — NO TRADE ES UNA DECISIÓN VÁLIDA
------------------------------------------
El sistema no debe verse obligado a comprar o vender.

REGLA 9 — BENCHMARKS
--------------------
Todo modelo complejo debe superar o justificar su uso frente a baselines simples.

Baselines mínimos:
- buy-and-hold;
- cash/no-trade;
- moving average;
- momentum;
- naive last-value;
- random/constant benchmark;
- estrategia técnica simple.

REGLA 10 — REPRODUCIBILIDAD
---------------------------
Fijar seeds cuando sea posible.
Registrar:
- versión de datos;
- configuración;
- hiperparámetros;
- commit;
- fecha;
- universo;
- costes;
- periodo.

===============================================================
5. MODELOS PRINCIPALES
===============================================================

5.1 TEMPORAL FUSION TRANSFORMER — TFT
--------------------------------------

Usar TFT como modelo principal de forecasting multi-horizon.

Horizontes configurables, por ejemplo:

- 1h
- 2h
- 4h
- 8h
- 12h
- 1d
- 3d
- 7d
- 14d
- 30d

No asumir que todos son apropiados para todos los mercados.

TFT debe poder trabajar con:

- static covariates;
- observed historical inputs;
- known future inputs;
- temporal features;
- categorical features cuando existan.

Outputs recomendados:
- expected return;
- quantiles;
- probability of positive return;
- probability of reaching target;
- forecast volatility;
- expected drawdown.

5.2 XGBOOST / LIGHTGBM
----------------------

Utilizar como:
- baseline fuerte;
- modelo tabular;
- componente del ensemble.

Features potenciales:
- returns;
- log returns;
- rolling volatility;
- RSI;
- MACD;
- moving averages;
- ATR;
- Bollinger Bands;
- momentum;
- volume;
- volume change;
- volatility regimes;
- drawdown;
- correlations;
- market breadth;
- macro variables;
- sentiment;
- fundamentals.

No agregar features solamente por cantidad.
Cada feature debe tener:
- definición;
- timestamp;
- fuente;
- justificación;
- disponibilidad histórica;
- riesgo de leakage.

5.3 LSTM / GRU
---------------

Implementar como benchmark deep learning y posible componente del ensemble.

No asumir superioridad frente a TFT.

5.4 GARCH / VOLATILITY MODELS
-----------------------------
Evaluar modelos estadísticos de volatilidad.

Objetivo:
- forecast de volatilidad;
- detección de régimen;
- input para risk management.

5.5 DeepLOB
-----------

Implementar solamente cuando exista acceso a datos de order book suficientemente completos.

No fingir que OHLCV equivale a order book.

5.6 ENSEMBLE
------------

Comparar:
- simple average;
- weighted average;
- stacking;
- meta-model.

Los pesos deben aprenderse exclusivamente dentro del entrenamiento/validación.

===============================================================
6. PREDICCIÓN PROBABILÍSTICA
===============================================================

No limitar el target a precio futuro.

Targets principales:

1. Return:
R_h = (P_t+h / P_t) - 1

2. Log return:
log(P_t+h / P_t)

3. Direction:
sign(R_h)

4. Target hit:
I(max_future_return >= target)

5. Stop hit:
I(min_future_return <= stop)

6. Maximum favorable excursion.

7. Maximum adverse excursion.

8. Future volatility.

9. Time-to-target.

10. Time-to-stop.

Crear targets para varios horizontes.

Ejemplo:

target_return_1h
target_return_4h
target_return_1d
target_return_7d

===============================================================
7. CONFORMAL PREDICTION
===============================================================

Implementar una capa de incertidumbre.

Objetivo:

Dado un forecast:

Predicción:
+7.4%

Producir:

Intervalo:
+3.1% — +11.8%

y medir cobertura real.

Implementar:
- split conformal;
- rolling conformal o adaptive conformal cuando sea apropiado;
- coverage evaluation;
- interval width;
- conditional coverage cuando sea posible.

Nunca llamar "95% confidence" a un intervalo sin definir exactamente qué significa.

Usar terminología consistente:
- prediction interval;
- empirical coverage;
- calibrated probability;
- confidence score.

===============================================================
8. CALIBRACIÓN
===============================================================

Evaluar:

- Reliability diagrams;
- Brier Score;
- Log Loss;
- Expected Calibration Error;
- Precision/Recall por threshold;
- ROC-AUC cuando corresponda;
- PR-AUC cuando haya clases desbalanceadas.

Una predicción 80% debe ocurrir aproximadamente 80% de las veces en el largo plazo bajo condiciones comparables.

Si no está calibrada:
- calibrate;
- report;
- no ocultar.

9. REINFORCEMENT LEARNING
===============================================================

Usar RL para DECISIÓN, no necesariamente para reemplazar el forecasting.

Primera implementación:
PPO.

Segunda:
SAC.

Comparar contra policy heurística.

STATE
-----

El estado puede contener:

- price;
- returns;
- volatility;
- volume;
- technical features;
- model forecasts;
- forecast intervals;
- market regime;
- current position;
- cash;
- unrealized PnL;
- drawdown;
- transaction history;
- transaction costs;
- portfolio exposure.

ACTION
------

Acciones discretas o continuas.

Ejemplo:

Discrete:
- HOLD;
- BUY;
- SELL;
- REDUCE;
- ADD.

Continuous:
position_target ∈ [0,1]

Esto permite decidir:
- 0%;
- 10%;
- 25%;
- 50%;
- 75%;
- 100%.

REWARD
------

Reward base:

Return
- lambda_risk * Risk
- lambda_cost * TransactionCost
- lambda_drawdown * Drawdown
- lambda_trade * NumberOfTrades

Evaluar distintas funciones y documentar la elegida.

===============================================================
10. POSITION SIZING
===============================================================

El sistema debe distinguir:

"¿Es buena oportunidad?"

de:

"¿Cuánto capital asigno?"

Nunca interpretar:
high confidence = all-in automáticamente.

Implementar risk constraints:

- max position;
- max daily loss;
- max drawdown;
- volatility scaling;
- exposure limit;
- concentration limit.

Opcionalmente evaluar:
- fixed fractional;
- volatility targeting;
- Kelly fraccional, SOLO como experimento y con límites estrictos.

No usar Kelly completo como recomendación operativa.

===============================================================
11. MULTIPLE TRANSACTIONS
===============================================================

El sistema debe poder producir:

SINGLE ENTRY:
100% entrada -> 100% salida

SCALING:
30% -> 30% -> 40%

DCA:
múltiples entradas condicionadas

PARTIAL EXIT:
25% -> 25% -> 50%

TRAILING:
salida dinámica

Pero no asumir que dividir operaciones siempre mejora resultados.

El modelo debe comparar:

Expected utility(strategy A)
vs
Expected utility(strategy B)

considerando:
- fees;
- slippage;
- execution risk;
- drawdown;
- opportunity cost.

- bullish trend;

===============================================================
13. RISK OVERLAY
===============================================================

Crear una capa independiente que pueda BLOQUEAR una decisión del modelo.

Ejemplo:

MODEL:
BUY — confidence 82%

RISK:
BLOCK

Razón:
- volatility extreme;
- liquidity insufficient;
- max drawdown breached;
- spread excessive.

El Risk Overlay tiene autoridad superior al modelo predictivo.

===============================================================

- risk overlay lo permite;
- liquidez lo permite;
- drawdown constraints lo permiten;
- incertidumbre está dentro del límite.

64. DEFINICIÓN DE "MEJOR MOMENTO"
===============================================================

No definir:

Definir:

"momento que, utilizando solamente información disponible en t, maximiza la utilidad esperada ajustada por riesgo."

Utilidad:

U = E(Return)
    - lambda1 * Risk
    - lambda2 * Drawdown
    - lambda3 * TransactionCosts
    - lambda4 * Uncertainty
    - lambda5 * Turnover

Los lambdas deben ser configurables y evaluados.
